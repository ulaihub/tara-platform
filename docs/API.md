# API Tara — guide pour les développeurs des applications

Le contrat complet est dans [`apps/api/openapi.json`](../apps/api/openapi.json), généré depuis le code et vérifié par la CI. En développement, l'interface Swagger est servie sur <http://localhost:3000/docs>.

Pour générer le client Dart des applications Flutter :

```bash
npx @openapitools/openapi-generator-cli generate -i apps/api/openapi.json -g dart-dio -o packages/api_client_dart
```

## Conventions

| Sujet       | Règle                                                                                                                                                                                                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adresse     | Toutes les routes sont sous `/v1`, sauf `/health`.                                                                                                                                                                                                                               |
| Connexion   | `Authorization: Bearer <accessToken>` sur toutes les routes, sauf `auth/*`, `public/*` et `/health`.                                                                                                                                                                             |
| Langue      | `Accept-Language: fr` ou `en`. Pour un utilisateur connecté, la langue de son compte prime.                                                                                                                                                                                      |
| Erreurs     | Toujours `{ "error": { "code", "message", "details?", "requestId?" } }`. L'app se fie à `code` (liste fermée dans le schéma `ErrorBody`) ; `message` est prêt à afficher ; `requestId` est à communiquer au support.                                                             |
| Argent      | Montants en FCFA entiers, devise `XAF`. Jamais de décimales.                                                                                                                                                                                                                     |
| Dates       | ISO 8601 en UTC (`2026-11-03T09:00:00.000Z`). L'app affiche l'heure du Cameroun (UTC+1).                                                                                                                                                                                         |
| Téléphones  | Toutes les écritures courantes sont acceptées (`690 00 00 00`, `+237690000000`…) et renvoyées au format `+2376XXXXXXXX`.                                                                                                                                                         |
| Pagination  | `?limit=20&cursor=<nextCursor>` ; la réponse contient `items` et `nextCursor` (`null` à la fin).                                                                                                                                                                                 |
| Idempotence | En-tête `Idempotency-Key` (UUID) : facultatif sur `POST /v1/orders` et `POST /v1/orders/batch`, **obligatoire** sur toute opération qui déplace de l'argent (recharge, retrait, dépôt, reversement, avoir). Renvoyer la même requête avec la même clé ne refait pas l'opération. |
| Fichiers    | `multipart/form-data`, champ `file`. Photos et notes vocales : 1 Mo au plus (compresser côté app, viser moins de 150 Ko). Pièces KYC : 5 Mo, JPEG, PNG, WebP ou PDF ; le contenu réel est vérifié.                                                                               |
| Limitation  | 120 requêtes par minute et par compte connecté ; sur les routes publiques, par adresse IP avec des seuils larges (les opérateurs partagent une même IP entre abonnés). Au-delà : `429` avec le code `RATE_LIMITED`.                                                              |

## Connexion par code SMS (A1)

1. `POST /v1/auth/otp` avec `{ phone }` : un code à 6 chiffres part par SMS, valable 5 minutes. Nouvelle demande possible après 60 secondes, 5 au plus par quart d'heure.
2. `POST /v1/auth/otp/verify` avec `{ challengeId, code, device }`. Pour un nouveau compte, la réponse est `422 TERMS_REQUIRED` : afficher les conditions puis renvoyer **le même code** avec `terms` (et `referralCode` si l'utilisateur en a un). Après 5 codes faux, il faut en demander un nouveau.
3. La réponse contient `accessToken` (15 minutes), `refreshToken` (30 jours) et `isNewUser`.
4. `POST /v1/auth/refresh` remplace la paire de jetons. Un jeton de rafraîchissement ne sert qu'une fois : le réutiliser ferme toutes les sessions du compte. Stocker le nouveau jeton avant toute autre action.
5. `POST /v1/auth/logout` ferme la session de l'appareil.

## Conditions d’utilisation acceptées et signées

Textes rédigés dans `docs/juridique` et copiés dans l’API par `pnpm --filter @tara/api legal` (un test vérifie la copie). Chaque app affiche **le texte complet**, une case à cocher non cochée par défaut, puis fait signer par un **code SMS**.

| Étape                       | Route                                                                                                                      | Points d’attention                                                                                                                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lire un texte (sans compte) | `GET /v1/legal/{expediteurs\|livreurs\|destinataires\|confidentialite}`                                                    | `version` (« 2026-11 »), `title`, `markdown` (titres `#`, listes `-`, tableaux, gras `**`).                                                                                                                                                                      |
| Inscription                 | `POST /v1/auth/otp/verify` avec `terms: { expediteurs: "2026-11", confidentialite: "2026-11" }` (app livreur : `livreurs`) | Le code de connexion signe l’acceptation. Version qui n’est plus en vigueur, confidentialité manquante ou conditions des deux apps à la fois : `409 TERMS_OUTDATED`, le code reste valable.                                                                      |
| À l’ouverture de l’app      | `GET /v1/me/terms?app=client\|rider`                                                                                       | `required` : textes à accepter (vide si tout est à jour) ; `accepted` : versions acceptées et date (copie consultable dans le profil).                                                                                                                           |
| Signer                      | `POST /v1/me/terms/code` puis `POST /v1/me/terms?app=…` avec `{ challengeId, code, versions, installationId }`             | Code SMS dédié (« code pour SIGNER… », 3 par heure). `versions` : celles affichées ; une version dépassée entre-temps donne `409 TERMS_OUTDATED`.                                                                                                                |
| Sans acceptation            | —                                                                                                                          | Expéditeur : `403 TERMS_ACCEPTANCE_REQUIRED` sur `POST /v1/orders` et `/batch`. Livreur : blocage `TERMS` dans `GET /v1/rider/presence`, passage en ligne refusé (`RIDER_NOT_ELIGIBLE`), plus aucune proposition de course, `403` sur l’acceptation d’une offre. |

Preuve gardée sur chaque consentement : version (`expediteurs:2026-11`), date et heure, adresse IP, application et appareil (`user_agent`, `installation_id`), plus une ligne `terms.accepted` au journal d’audit. `POST /v1/me/consents` ne sert plus qu’aux choix `LOCATION` et `MARKETING`.

## Double authentification de l’équipe

Les comptes ayant un rôle d’équipe (`DISPATCHER`, `SUPPORT`, `FINANCE`, `ADMIN`) doivent confirmer un code TOTP (Google Authenticator, Microsoft Authenticator, Aegis…). Sans vérification depuis moins de 12 heures, l’API répond `403 MFA_REQUIRED` sur le back-office, avec `details.enrolled`, et le compte n’a aucun droit d’équipe ailleurs.

1. Premier passage (`enrolled: false`) : `POST /v1/auth/mfa/setup` renvoie `otpauthUrl`, à afficher en QR code, puis `POST /v1/auth/mfa/activate` avec `{ code, refreshToken }`.
2. Ensuite (`enrolled: true`) : `POST /v1/auth/mfa/verify` avec `{ code, refreshToken }`.
3. Les deux renvoient une nouvelle paire de jetons, à utiliser à la place de l’ancienne.

Après 5 codes faux, le second facteur est bloqué 15 minutes (`MFA_LOCKED`). Téléphone perdu : un administrateur appelle `POST /v1/admin/users/{id}/mfa/reset`.

## Données personnelles (loi n° 2024/017)

- `GET /v1/me/export` : toutes les données du compte, en fichier JSON (3 fois par heure au plus).
- Suppression du compte : `POST /v1/me/deletion/code` envoie un code SMS dédié, puis `POST /v1/me/deletion` avec `{ challengeId, code }`. Refusée pour un livreur ou l’équipe (passer par le support), et tant qu’une commande est en cours.
- Les coordonnées des destinataires sont masquées 30 jours après la fin de la commande.
- Trajet des courses : points détaillés effacés 90 jours après la course, sauf litige (ticket ouvert) ou incident (alerte non traitée) ; le résumé (distance, durées, arrêts) reste avec la commande. Le livreur retrouve ses trajets dans `GET /v1/me/export`.

## Trajet des courses (sécurité, litiges, fraude)

Chaque position reçue pendant une course (de l'acceptation à la livraison, au retour ou à l'annulation) est enregistrée, un point toutes les ~10 s ; jamais en dehors d'une course. Les points ne sont jamais modifiés (le compte de l'API n'en a pas le droit).

| Qui     | Route                                                                                                              | Points d'attention                                                                                                                                                                                                                                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Livreur | `POST /v1/rider/orders/{id}/track` `{ points: [{ latitude, longitude, recordedAt, accuracy?, speed?, mocked? }] }` | Positions gardées sur le téléphone sans réseau (720 au plus par envoi). Seuls les points de la course sont gardés (`ignored` pour les autres) ; un renvoi est sans effet. `mocked` : position simulée signalée par Android.                                                                                                                               |
| Équipe  | `GET /v1/admin/orders/{id}/track`                                                                                  | Support, dispatch, administrateur : points, résumé et alertes. Chaque consultation est tracée dans le journal d'audit.                                                                                                                                                                                                                                    |
| Équipe  | `GET /v1/admin/course-alerts?status=open\|all`, `POST /v1/admin/course-alerts/{id}/acknowledge`                    | Alertes (une par sujet et par course, aussi en temps réel : `ops.course-alert`) : `ACTION_FAR` (enlèvement, livraison, échec ou retour déclaré à plus de 200 m de l'adresse), `LONG_STOP` (plus de 15 min au même endroit avec le colis, loin du vendeur et du client), `MOCK_LOCATION` (position simulée), `TRACK_GAP` (aucune position pendant 20 min). |

## Back-office d'exploitation (H1 à H8)

Le back-office (`apps/backoffice`) appelle l'API depuis son serveur avec le jeton du membre
de l'équipe (second facteur vérifié) ; le navigateur ne voit jamais ce jeton. `GET /me`
indique où en est le second facteur (`staff.mfaEnrolled`, `staff.mfaVerified`).

**Carte en direct (H1)** : `GET /admin/live-map` (`ADMIN`, `DISPATCHER`, `SUPPORT`), lue
toutes les 5 secondes par le back-office. Elle donne :

- les livreurs validés et ceux en course : `FREE` (en ligne, sans course), `ON_COURSE`,
  `OFFLINE`, dernière position (gardée 15 min), `signalLost` quand un livreur en ligne
  n'envoie plus de position depuis `RIDER_POSITION_TTL_SECONDS` ;
- les commandes en cours (les programmées une heure avant leur départ) avec leur retard :
  `NO_RIDER` (recherche au-delà de `DISPATCH_ALERT_AFTER_SECONDS`), `PICKUP` (pas enlevée
  `LATE_PICKUP_MINUTES` après l'attribution, 25 par défaut), `DELIVERY` (pas livrée après
  le trajet estimé à 300 m/min plus `LATE_DELIVERY_MARGIN_MINUTES`, 15 par défaut ; après
  un échec, le compte repart de l'échec) ; `awaitingValidation` (remise sans code à valider)
  et `awaitingDecision` (échec, choix de l'expéditeur attendu) ;
- les alertes de sécurité non closes et les alertes de trajet pas encore vues.

Avec OSRM (`OSRM_URL`), chaque livreur porte aussi `roadPosition` : sa position ramenée sur
la rue la plus proche (à moins de 40 m, sinon null), calculée une fois par nouvelle position.

**Course d'un livreur sur la carte** : `GET /admin/riders/{riderId}/trail?orderId=`
(mêmes rôles). Pour la course en cours (la plus récente, ou `orderId`) : `traveled`, le
chemin parcouru depuis l'acceptation, recalé sur les rues par OSRM (`match`) ou, à défaut,
les positions GPS reliées (`onRoads: false`) ; `remaining`, l'itinéraire routier jusqu'au
prochain arrêt (vendeur, client, ou rien si une décision est attendue après un échec), avec
distance et durée prudente (au moins 18 km/h de moyenne). Rien en dehors des courses : seul
le trajet enregistré pendant la course est lu.

## Cycle de vie d'une commande à sa création

- Paiement en espèces ou par le destinataire, sans créneau : la commande passe aussitôt en `SEARCHING_RIDER`.
- Prépaiement Mobile Money ou portefeuille : elle reste en `CREATED` jusqu'au paiement (phase 3).
- Créneau programmé : elle reste en `CREATED` et part en recherche de livreur 20 minutes avant le créneau.

Le code d'enlèvement (4 chiffres) n'est renvoyé qu'une fois, à la création ; s'il est perdu, `POST /orders/{id}/pickup-code` en génère un nouveau. Le code de livraison est créé à l'enlèvement et envoyé au destinataire (WhatsApp, ou SMS en repli). Après 5 codes faux saisis par le livreur, le code est bloqué : nouveau code d'enlèvement par l'expéditeur, validation de la livraison par le support.

## Attribution des courses (D1 à D4)

1. Dès qu'une commande passe en `SEARCHING_RIDER`, elle est proposée au livreur en ligne le mieux placé : distance d'approche, courses en cours, espèces détenues et note.
2. Il a 30 secondes pour répondre. Refus ou silence : la course part au suivant. Après 3 tours sans preneur, elle est diffusée à 5 livreurs à la fois ; le premier qui accepte l'emporte.
3. Le rayon de recherche s'élargit (3, 5, 8 puis 12 km). Sans livreur, nouvelle tentative toutes les 20 secondes ; après 5 minutes, le dispatch est alerté (temps réel et SMS d'astreinte), une seule fois.
4. Sont exclus : pièces manquantes ou expirées, plafond d'espèces atteint (en comptant les espèces de la course), 2 courses déjà en cours, une autre proposition en attente. Un livreur qui a refusé ou rendu la course ne la revoit pas.

Le dispatcheur voit les livreurs proches et la raison de chaque exclusion (`GET /admin/orders/{id}/candidates`), l'historique des propositions (`GET /admin/orders/{id}/dispatch`), et peut attribuer ou réattribuer à la main (`POST /admin/orders/{id}/assign`) ; le livreur retiré est prévenu.

Tous les délais sont réglables par variables d'environnement (`DISPATCH_*`, voir `.env.example`).

**Hors ligne (E7).** Chaque action accepte `latitude`, `longitude`, `occurredAt` (heure de l'action sur le téléphone, 72 h au plus) et `clientEventId` (identifiant unique généré par l'app). L'app met les actions en file sans réseau et les renvoie au retour du réseau : une action déjà reçue n'est pas refaite et la réponse donne l'état actuel de la course.

Back-office : `POST /admin/orders/{id}/validate-delivery` (support ; au-delà de `SUPPORT_VALIDATION_LIMIT` FCFA à encaisser, administrateur), `POST /admin/orders/{id}/failure-decision` (le support choisit à la place de l'expéditeur après un échec ; action tracée), `GET /admin/safety-alerts`, `POST /admin/safety-alerts/{id}/acknowledge`, `POST /admin/safety-alerts/{id}/police-called` (police appelée par l'agent quand le livreur est injoignable ou le danger confirmé : heure, agent et note gardés, action tracée), `POST /admin/safety-alerts/{id}/resolve`.

## Temps réel (F1)

Connexion Socket.IO sur l'espace `/realtime` (même hôte que l'API), avec le jeton d'accès :

```js
const socket = io('https://api.tara.cm/realtime', {
  auth: { token: accessToken },
  transports: ['websocket'],
});
```

Jeton absent ou invalide : erreur de connexion `UNAUTHENTICATED`. À l'expiration du jeton, le serveur envoie `session.expired` puis coupe : se reconnecter avec un jeton renouvelé.

## Notifications (F3)

- **Push** (Firebase Cloud Messaging) : l'app envoie son jeton après la connexion et à chaque renouvellement, `PUT /v1/me/devices/{installationId}/push-token` (`null` pour arrêter). Les propositions de course sont en priorité haute sur le canal Android `offers` (son et réveil écran verrouillé) ; les autres sur le canal `orders`. `data.type` indique l'écran à ouvrir.
- **Destinataire** (sans compte) : WhatsApp d'abord, avec des modèles approuvés par Meta nommés `tara_<modèle>` ; SMS si WhatsApp refuse le message ou signale plus tard un échec (webhook `POST /v1/webhooks/whatsapp`, signé).
- Messages par statut : confirmation au destinataire à la création ; push à l'expéditeur à l'attribution, à l'enlèvement, au départ, à la livraison, à l'échec, au retour et à l'annulation ; code de livraison puis reçu au destinataire ; au livreur, annulation ou retrait de sa course.

## Argent (G1 à G8, E5)

Montants en FCFA entiers. Chaque mouvement est une écriture du grand livre ; les soldes affichés en sont tirés.

**Paiement des frais d'une commande (G1).**

| `feePaymentMethod` (payé par l'expéditeur) | Ce qui se passe                                                                                                                                                                                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CASH`                                     | Payé au livreur à l'enlèvement ; la commande part tout de suite.                                                                                                                                                                                                                                             |
| `WALLET`                                   | Débité du solde Tara à la création (`INSUFFICIENT_BALANCE` sinon) ; pour un marchand, de son portefeuille.                                                                                                                                                                                                   |
| `MOMO_MTN`, `MOMO_ORANGE`                  | La commande reste `CREATED` ; `POST /orders/{id}/pay` envoie la demande au téléphone ; elle part à la confirmation. Lot (C4) : `POST /orders/batches/{id}/pay`, une seule demande pour toutes les commandes encore à payer, réparties à la confirmation (une commande annulée entre-temps revient au solde). |

Avec `feePayer: RECIPIENT`, le destinataire paie à la porte. Une commande annulée avant l'enlèvement rend ses frais au solde (avoir). Un retour que le destinataire devait payer est facturé à l'expéditeur. Un client dont le solde est négatif doit le régler avant de commander (`WALLET_IN_DEBT`) ; une boutique peut devoir jusqu'à 3 000 FCFA (`MERCHANT_DEBT_LIMIT`), au-delà ses nouvelles commandes attendent le règlement (`MERCHANT_DEBT_LIMIT`). Un compte endetté ne peut pas être supprimé (`ACCOUNT_HAS_DEBT`).

**Frais d'échec (E6).** Figés à la commande et annoncés au devis (`retryFee`, `returnFee` du devis et de `pricing`) : nouvelle tentative (supplément `FAILED_ATTEMPT` de la grille, 500 FCFA) et retour (supplément `RETURN`, la moitié du prix de base), à la charge de l'expéditeur et partagés comme la course (part du livreur de la grille). Une seule nouvelle tentative (`failure.retryAllowed`, sinon `RETRY_LIMIT_REACHED`). La tentative est prise sur le solde de l'expéditeur jusqu'à son plafond de dette (0 pour un particulier) ; au-delà, `RETRY_PAYMENT_REQUIRED` indique le montant à recharger (`POST /v1/me/wallet/topup`) avant de choisir. Retour : pas de paiement, pas de colis. Ce que le solde ne couvre pas (frais de retour, et la course si le destinataire devait la payer) est encaissé par le livreur à la remise (`GET /rider/orders/{id}/collection`, `reason: RETURN`, puis `POST /rider/orders/{id}/collect` en espèces ou par Mobile Money au téléphone de l'expéditeur) ; sinon `POST /rider/orders/{id}/return` répond `RETURN_COLLECTION_REQUIRED`. Le support peut clore un retour sans paiement (colis gardé au bureau).

**Encaissement à la porte (E5).** `GET /rider/orders/{id}/collection` donne ce qui reste dû (frais du destinataire et contre-remboursement). `POST /rider/orders/{id}/collect` avec `{ "method": "CASH" }` l'enregistre tout de suite (faisable hors connexion : `clientEventId`, `occurredAt`, position ; renvoyé, il est sans effet) ; avec `{ "method": "MOBILE_MONEY", "phone", "operator" }`, une demande part au téléphone du destinataire et la confirmation arrive par l'événement `payment.status` (ou `GET /payments/{id}`). La livraison est refusée (`COLLECTION_REQUIRED`) tant que tout n'est pas encaissé. Frais d'encaissement : 2 %, minimum 250 FCFA, déduits du montant reversé au marchand.

**Portefeuilles.**

| Qui      | Routes                                                                                                                                                                                                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client   | `GET /me/wallet` (boutique : encaissé aujourd'hui et livraisons du jour), `GET /me/wallet/transactions`, `POST /me/wallet/topup`, `POST /me/wallet/refund` (vers Mobile Money)                                                                                                                                                                      |
| Marchand | Idem avec `account=merchant` ; `POST /me/merchant/payouts` (à la demande, offres Pro et Business) ; `GET /me/payouts` ; `GET /me/merchant/statements/{AAAA-MM}` (PDF)                                                                                                                                                                               |
| Livreur  | `GET /rider/wallet` (solde prépayé `earnings`, mis de côté `reserved`, disponible ; espèces d'avant le solde prépayé : `cashHeld`, `cashDueBy`, `cashOverdue`), `POST /rider/topups` (recharge Mobile Money, frais payés par Tara), `GET /rider/wallet/transactions?account=earnings\|cash`, `POST /rider/withdrawals`, `POST /rider/cash-deposits` |

Le livreur garde sa part sur les espèces qu'il encaisse : son disponible au retrait vaut ses gains moins les espèces qu'il détient. Au-delà de son plafond d'espèces, il ne reçoit plus de courses tant qu'il n'a pas déposé.

**Reversements (G3).** Chaque jour à 18 h (heure du Cameroun), le portefeuille de chaque marchand en reversement quotidien part vers son numéro Mobile Money (500 FCFA minimum). Au-delà de 200 000 FCFA, un responsable financier valide d'abord. Un reversement échoué rend le montant au portefeuille.

**Solde prépayé du livreur (G5, décision 36).** Le solde (`earnings`) reçoit les gains et les recharges (`POST /rider/topups` par Mobile Money, crédité du montant entier : Tara paie les frais ; au bureau : `POST /admin/finance/riders/{riderId}/topups`). Une course avec encaissement (contre-remboursement, frais payés en espèces) n'est proposée qu'à un livreur dont le disponible la couvre (`BALANCE_TOO_LOW` sinon) ; à l'acceptation, le montant est mis de côté (`reserved`, `RIDER_BALANCE_TOO_LOW` si le solde a baissé entre-temps) ; à l'encaissement en espèces, il est pris sur le solde et le marchand est crédité aussitôt ; la réservation est libérée à la fin de la course ou si elle est retirée au livreur. Le solde ne devient jamais négatif. Disponible au retrait : solde − mis de côté.

**Espèces d'avant le solde prépayé.** Les espèces encore dues (`cashHeld`) se déposent sous 24 h (`CASH_DEPOSIT_DEADLINE_HOURS`), par Mobile Money (`POST /rider/cash-deposits`) ou au bureau ; rappel à 18 h ; en retard, plus de courses ni de passage en ligne (`CASH_OVERDUE`) ; 72 h de retard (`CASH_OVERDUE_SUSPEND_HOURS`) : compte suspendu, gains retenus sur la dette, SMS à l'équipe ; suspension levée par la finance.

**Back-office finance** (`ADMIN`, `FINANCE`, double authentification) : `GET /admin/finance/overview`, `GET /admin/finance/payouts`, `POST /admin/finance/payouts/{id}/approve` et `/reject`, `POST /admin/finance/riders/{riderId}/cash-deposits` (dépôt au bureau), `POST /admin/finance/users/{userId}/credits` (avoir), `POST /admin/finance/treasury-transfers`, `GET /admin/finance/reconciliations`, `POST /admin/finance/reconciliations/{jour}/run`, `GET /admin/finance/journal.csv?from&to` (export comptable, séparateur point-virgule), `GET /admin/finance/merchants/{merchantId}/statements/{AAAA-MM}`.

Notifications de l'agrégateur : `GET` ou `POST /v1/webhooks/payments/{prestataire}`, signées.
