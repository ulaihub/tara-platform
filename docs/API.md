# API Tara — guide pour les développeurs des applications

Le contrat complet est dans [`apps/api/openapi.json`](../apps/api/openapi.json), généré depuis le code et vérifié par la CI. En développement, l'interface Swagger est servie sur <http://localhost:3000/docs>.

Pour générer le client Dart des applications Flutter :

```bash
npx @openapitools/openapi-generator-cli generate -i apps/api/openapi.json -g dart-dio -o packages/api_client_dart
```

## Conventions

| Sujet       | Règle                                                                                                                                                                                                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adresse     | Toutes les routes sont sous `/v1`, sauf `/health`.                                                                                                                                                                                                                               |
| Connexion   | `Authorization: Bearer <accessToken>` sur toutes les routes, sauf `auth/*`, `public/*` et `/health`.                                                                                                                                                                             |
| Langue      | `Accept-Language: fr` ou `en`. Pour un utilisateur connecté, la langue de son compte prime.                                                                                                                                                                                      |
| Erreurs     | Toujours `{ "error": { "code", "message", "details?", "requestId?" } }`. L'app se fie à `code` (liste fermée dans le schéma `ErrorBody`) ; `message` est prêt à afficher ; `requestId` est à communiquer au support.                                                             |
| Argent      | Montants en FCFA entiers, devise `XAF`. Jamais de décimales.                                                                                                                                                                                                                     |
| Dates       | ISO 8601 en UTC (`2026-11-03T09:00:00.000Z`). L'app affiche l'heure du Cameroun (UTC+1).                                                                                                                                                                                         |
| Téléphones  | Toutes les écritures courantes sont acceptées (`690 00 00 00`, `+237690000000`…) et renvoyées au format `+2376XXXXXXXX`.                                                                                                                                                         |
| Pagination  | `?limit=20&cursor=<nextCursor>` ; la réponse contient `items` et `nextCursor` (`null` à la fin).                                                                                                                                                                                 |
| Idempotence | En-tête `Idempotency-Key` (UUID) : facultatif sur `POST /v1/orders` et `POST /v1/orders/batch`, **obligatoire** sur toute opération qui déplace de l'argent (recharge, retrait, dépôt, reversement, avoir). Renvoyer la même requête avec la même clé ne refait pas l'opération. |
| Fichiers    | `multipart/form-data`, champ `file`. Photos et notes vocales : 1 Mo au plus (compresser côté app, viser moins de 150 Ko). Pièces KYC : 5 Mo, JPEG, PNG, WebP ou PDF ; le contenu réel est vérifié.                                                                               |
| Limitation  | 120 requêtes par minute et par compte connecté ; sur les routes publiques, par adresse IP avec des seuils larges (les opérateurs partagent une même IP entre abonnés). Au-delà : `429` avec le code `RATE_LIMITED`.                                                              |

## Connexion par code WhatsApp ou SMS (A1)

1. `POST /v1/auth/otp` avec `{ phone, appHash?, channel? }` : un code à 6 chiffres, valable 5 minutes, part par WhatsApp quand `WHATSAPP_OTP` est activé (modèle `tara_otp`, bouton « Copier le code »), sinon par SMS. `channel: "SMS"` force le SMS (« Recevoir par SMS »). Si WhatsApp refuse le message, ou si Meta signale plus tard un échec, le SMS part en secours tant que le code est valable. `appHash` : empreinte de l'app Android (11 caractères) ; si elle figure dans `SMS_APP_HASHES`, elle termine le SMS et Android remet le code à l'app sans rien demander. Réponse : `channel` (`WHATSAPP` ou `SMS`) et `autoRead` (empreinte ajoutée). Nouvelle demande possible après 60 secondes, 5 au plus par quart d'heure.
2. `POST /v1/auth/otp/verify` avec `{ challengeId, code, device }`. Pour un nouveau compte, la réponse est `422 TERMS_REQUIRED` : afficher les conditions puis renvoyer **le même code** avec `terms` (et `referralCode` si l'utilisateur en a un). Après 5 codes faux, il faut en demander un nouveau.
3. La réponse contient `accessToken` (15 minutes), `refreshToken` (90 jours, prolongés à chaque renouvellement) et `isNewUser`.
4. `POST /v1/auth/refresh` remplace la paire de jetons. Un jeton de rafraîchissement ne sert qu'une fois : le réutiliser ferme toutes les sessions du compte. Stocker le nouveau jeton avant toute autre action.
5. `POST /v1/auth/logout` ferme la session de l'appareil.

## Conditions d’utilisation acceptées et signées

Textes rédigés dans `docs/juridique` et copiés dans l’API par `pnpm --filter @tara/api legal` (un test vérifie la copie). Chaque app affiche **le texte complet**, lu jusqu’en bas, et une case à cocher non cochée par défaut. À l’inscription, le code SMS de connexion signe l’acceptation ; une nouvelle version s’accepte ensuite avec la case seule, la session de l’utilisateur connecté faisant foi.

| Étape                       | Route                                                                                                                      | Points d’attention                                                                                                                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lire un texte (sans compte) | `GET /v1/legal/{expediteurs\|livreurs\|destinataires\|confidentialite}`                                                    | `version` (« 2026-11 »), `title`, `markdown` (titres `#`, listes `-`, tableaux, gras `**`).                                                                                                                                                                      |
| Inscription                 | `POST /v1/auth/otp/verify` avec `terms: { expediteurs: "2026-11", confidentialite: "2026-11" }` (app livreur : `livreurs`) | Le code de connexion signe l’acceptation. Version qui n’est plus en vigueur, confidentialité manquante ou conditions des deux apps à la fois : `409 TERMS_OUTDATED`, le code reste valable.                                                                      |
| À l’ouverture de l’app      | `GET /v1/me/terms?app=client\|rider`                                                                                       | `required` : textes à accepter (vide si tout est à jour) ; `accepted` : versions acceptées et date (copie consultable dans le profil).                                                                                                                           |
| Accepter                    | `POST /v1/me/terms?app=…` avec `{ versions, installationId }`                                                              | Sans code : la session suffit. `versions` : celles affichées ; une version dépassée entre-temps donne `409 TERMS_OUTDATED`. Anciennes apps : `POST /v1/me/terms/code` puis `challengeId` et `code` en plus, encore vérifiés (les deux ou aucun).                 |
| Sans acceptation            | —                                                                                                                          | Expéditeur : `403 TERMS_ACCEPTANCE_REQUIRED` sur `POST /v1/orders` et `/batch`. Livreur : blocage `TERMS` dans `GET /v1/rider/presence`, passage en ligne refusé (`RIDER_NOT_ELIGIBLE`), plus aucune proposition de course, `403` sur l’acceptation d’une offre. |

Preuve gardée sur chaque consentement : version (`expediteurs:2026-11`), date et heure, adresse IP, application et appareil (`user_agent`, `installation_id`), plus une ligne `terms.accepted` au journal d’audit. `POST /v1/me/consents` ne sert plus qu’aux choix `LOCATION` et `MARKETING`.

## Code secret et empreinte digitale

Code à 4 chiffres, comme Orange Money et MTN MoMo, demandé dans les apps pour afficher le solde, retirer de l'argent et supprimer le compte. Haché (scrypt et secret du serveur), jamais gardé en clair.

| Route                                                          | Effet                                                                                                                                                                         |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/me/pin`                                               | `set`, `locked`, `remainingAttempts`.                                                                                                                                         |
| `PUT /v1/me/pin` `{ pin, currentPin? \| challengeId + code? }` | Premier code librement ; ensuite avec le code actuel, ou avec un code `PIN_RESET` reçu (`POST /v1/me/pin/code`). Codes trop simples refusés (`PIN_TOO_SIMPLE` : 1111, 1234…). |
| `POST /v1/me/pin/verify` `{ pin \| biometricKey }`             | Vérifie avant d'afficher le solde.                                                                                                                                            |
| `POST /v1/me/pin/biometric` `{ pin, installationId }`          | Active l'empreinte sur ce téléphone : renvoie une clé gardée dans le stockage chiffré, libérée par le capteur, qui remplace le code.                                          |
| `DELETE /v1/me/pin/biometric?installationId=`                  | Désactive l'empreinte de ce téléphone.                                                                                                                                        |

Une fois le code choisi, `pin` ou `biometricKey` est exigé dans le corps des retraits (`/v1/rider/withdrawals`, `/v1/me/wallet/refund`, `/v1/me/merchant/payouts`) et de la suppression du compte (`/v1/me/deletion`, qui accepte encore le code SMS des anciennes apps). Erreurs : `PIN_REQUIRED`, `PIN_INVALID` (essais restants), `PIN_LOCKED` après 5 erreurs (nouveau code via `PIN_RESET` ; les clés d'empreinte sont effacées), `BIOMETRIC_INVALID`. Sans code choisi, les retraits passent comme avant (anciennes apps) ; les nouvelles apps le font choisir à la première action d'argent.

## Double authentification de l’équipe

Les comptes ayant un rôle d’équipe (`DISPATCHER`, `SUPPORT`, `FINANCE`, `ADMIN`) doivent confirmer un code TOTP (Google Authenticator, Microsoft Authenticator, Aegis…). Sans vérification depuis moins de 12 heures, l’API répond `403 MFA_REQUIRED` sur le back-office, avec `details.enrolled`, et le compte n’a aucun droit d’équipe ailleurs.

1. Premier passage (`enrolled: false`) : `POST /v1/auth/mfa/setup` renvoie `otpauthUrl`, à afficher en QR code, puis `POST /v1/auth/mfa/activate` avec `{ code, refreshToken }`.
2. Ensuite (`enrolled: true`) : `POST /v1/auth/mfa/verify` avec `{ code, refreshToken }`.
3. Les deux renvoient une nouvelle paire de jetons, à utiliser à la place de l’ancienne.

Après 5 codes faux, le second facteur est bloqué 15 minutes (`MFA_LOCKED`). Téléphone perdu : un administrateur appelle `POST /v1/admin/users/{id}/mfa/reset`.

## Données personnelles (loi n° 2024/017)

- `GET /v1/me/export` : toutes les données du compte, en fichier JSON (3 fois par heure au plus).
- Suppression du compte : `POST /v1/me/deletion/code` envoie un code SMS dédié, puis `POST /v1/me/deletion` avec `{ challengeId, code }`. Refusée pour un livreur ou l’équipe (passer par le support), et tant qu’une commande est en cours.
- Les coordonnées des destinataires sont masquées 30 jours après la fin de la commande.
- Trajet des courses : points détaillés effacés 90 jours après la course, sauf litige (ticket ouvert) ou incident (alerte non traitée) ; le résumé (distance, durées, arrêts) reste avec la commande. Le livreur retrouve ses trajets dans `GET /v1/me/export`.

## Trajet des courses (sécurité, litiges, fraude)

Chaque position reçue pendant une course (de l'acceptation à la livraison, au retour ou à l'annulation) est enregistrée, un point toutes les ~10 s ; jamais en dehors d'une course. Les points ne sont jamais modifiés (le compte de l'API n'en a pas le droit).

| Qui     | Route                                                                                                              | Points d'attention                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Livreur | `POST /v1/rider/orders/{id}/track` `{ points: [{ latitude, longitude, recordedAt, accuracy?, speed?, mocked? }] }` | Positions gardées sur le téléphone sans réseau (720 au plus par envoi). Seuls les points de la course sont gardés (`ignored` pour les autres) ; un renvoi est sans effet. `mocked` : position simulée signalée par Android.                                                                                                                                                                                                                                                                          |
| Équipe  | `GET /v1/admin/orders/{id}/track`                                                                                  | Support, dispatch, administrateur : points, résumé et alertes. Chaque consultation est tracée dans le journal d'audit.                                                                                                                                                                                                                                                                                                                                                                               |
| Équipe  | `GET /v1/admin/course-alerts?status=open\|all`, `POST /v1/admin/course-alerts/{id}/acknowledge`                    | Alertes (une par sujet et par course, aussi en temps réel : `ops.course-alert`) : `ACTION_FAR` (enlèvement, livraison, échec ou retour déclaré à plus de 200 m de l'adresse), `LONG_STOP` (plus de 15 min au même endroit avec le colis, loin du vendeur et du client), `MOCK_LOCATION` (position simulée), `TRACK_GAP` (aucune position pendant 20 min), `APPROACH_BONUS` (prime d'approche payée alors que le trajet enregistré jusqu'au vendeur fait moins de la moitié de la distance annoncée). |

## Back-office d'exploitation (H1 à H8)

Le back-office (`apps/backoffice`) appelle l'API depuis son serveur avec le jeton du membre
de l'équipe (second facteur vérifié) ; le navigateur ne voit jamais ce jeton. `GET /me`
indique où en est le second facteur (`staff.mfaEnrolled`, `staff.mfaVerified`).

**Carte en direct (H1)** : `GET /admin/live-map` (`ADMIN`, `DISPATCHER`, `SUPPORT`), lue
toutes les 5 secondes par le back-office. Elle donne :

- les livreurs validés et ceux en course : `FREE` (en ligne, sans course), `ON_COURSE`,
  `OFFLINE`, dernière position (gardée 15 min), `signalLost` quand un livreur en ligne
  n'envoie plus de position depuis `RIDER_POSITION_TTL_SECONDS` ;
- les commandes en cours (les programmées une heure avant leur départ) avec leur retard :
  `NO_RIDER` (recherche au-delà de `DISPATCH_ALERT_AFTER_SECONDS`), `PICKUP` (pas enlevée
  `LATE_PICKUP_MINUTES` après l'attribution, 25 par défaut), `DELIVERY` (pas livrée après
  le trajet estimé à 300 m/min plus `LATE_DELIVERY_MARGIN_MINUTES`, 15 par défaut ; après
  un échec, le compte repart de l'échec) ; `awaitingValidation` (remise sans code à valider)
  et `awaitingDecision` (échec, choix de l'expéditeur attendu) ;
- les alertes de sécurité non closes et les alertes de trajet pas encore vues.

Avec OSRM (`OSRM_URL`), chaque livreur porte aussi `roadPosition` : sa position ramenée sur
la rue la plus proche (à moins de 40 m, sinon null), calculée une fois par nouvelle position.

**Course d'un livreur sur la carte** : `GET /admin/riders/{riderId}/trail?orderId=`
(mêmes rôles). Pour la course en cours (la plus récente, ou `orderId`) : `traveled`, le
chemin parcouru depuis l'acceptation, recalé sur les rues par OSRM (`match`) ou, à défaut,
les positions GPS reliées (`onRoads: false`) ; `remaining`, l'itinéraire routier jusqu'au
prochain arrêt (vendeur, client, ou rien si une décision est attendue après un échec), avec
distance et durée prudente (au moins 18 km/h de moyenne). Rien en dehors des courses : seul
le trajet enregistré pendant la course est lu.

**Livreurs (H3)** (dispatch et administrateurs) :

- `GET /admin/riders?view=&q=&limit=&cursor=` : vues `TO_REVIEW` (candidature en attente ou
  pièce envoyée à examiner), `PENDING`, `ACTIVE`, `SUSPENDED`, `REJECTED`, `ALL` ; recherche
  par nom, numéro (saisie en chiffres) ou plaque (avec ou sans espaces) ; `counts` donne le
  nombre de livreurs par vue. Chaque livreur porte ses pièces, la note moyenne,
  les courses livrées en 30 jours et les pièces qui expirent dans les 30 jours.
- Un candidat est validé (`decision: APPROVE`) dès que toutes ses pièces exigées sont
  validées ; aucun entretien n'est demandé.
- `GET /admin/riders/{id}/reliability` : sur 30 jours et depuis l'inscription, propositions
  acceptées, refusées ou sans réponse, courses livrées et à l'heure, échecs déclarés, colis
  refusés à l'enlèvement, notes, temps en ligne, alertes de course et SOS ; historique des
  décisions lu dans le journal d'audit (pièces examinées, validation, refus,
  suspension, réactivation, suspension faute de dépôt, seuil de retrait gratuit).
- Le back-office ouvre une pièce (`GET /admin/kyc-documents/{id}/file`, consultation tracée)
  dans un onglet isolé : images seulement affichées, PDF téléchargés.

**Service client (H6)** :

- Apps (tout utilisateur connecté) : `POST /support/tickets` (`category`, `subject`,
  `message`, `orderId` d'une commande qu'il envoie, reçoit ou livre), `GET /support/tickets`,
  `GET /support/tickets/{id}`, `POST /support/tickets/{id}/messages`. Cinq demandes en cours
  au plus (`TICKET_LIMIT_REACHED`) ; colis perdu et paiement en priorité haute ; une demande
  résolue est rouverte par une réponse du client, une demande close ne l'est plus
  (`TICKET_CLOSED`). Les notes internes ne sont jamais renvoyées.
- Back-office (support et administrateurs) : `GET /admin/support/tickets?view=&q=` (vues
  `TO_HANDLE`, `MINE`, `URGENT`, `RESOLVED`, `ALL` ; recherche par `SUP-…`, commande,
  téléphone ou sujet ; urgentes puis plus anciennes d'abord ; `counts` par vue),
  `POST /admin/support/tickets` (après un appel : `phone` et/ou `orderReference`, même pour une
  personne sans compte ; la demande est confiée à qui l'ouvre), `GET /admin/support/tickets/{id}`,
  `POST /admin/support/tickets/{id}/messages` (`internal` : note interne ; sinon le client est
  prévenu par notification, à défaut par SMS `SUPPORT_REPLY` ; sans l'app, `requesterHasApp`
  est faux et le back-office demande à l'équipe d'appeler la personne), `PATCH /admin/support/tickets/{id}`
  (`status`, `priority`, `assigneeId`, tracé).
- Litiges (support, dispatch, administrateurs) : `GET /admin/support/orders/{id}/evidence`
  (preuves : heure, position, code vérifié, photo, appels du livreur avant un échec ; notes ;
  photo du colis ; points du trajet), `GET /admin/support/proofs/{id}/photo` et
  `GET /admin/support/orders/{id}/parcel-photo` (consultations tracées).

**Commandes (H2)** :

- `GET /admin/orders?q=&view=&from=&to=&riderId=&limit=&cursor=` (dispatch, support,
  administrateurs) : recherche par référence, numéro ou nom du destinataire, expéditeur ou
  boutique ; vues `all`, `active`, `problems` (échec en attente, recherche sans livreur
  signalée, remise sans code, alerte de trajet non vue, retard), `delivered`, `cancelled`
  (annulées ou retournées) ; jours de création à l'heure de Douala ; du plus récent au plus
  ancien, avec le total.
- `GET /admin/orders/{id}` : fiche complète (colis, personnes, arrêts, prix et parts,
  encaissement, échec, historique des statuts avec l'auteur, preuves, alertes de trajet,
  notes internes, actions possibles).
- `POST /admin/orders/{id}/notes` : note interne (jamais montrée aux clients ni aux
  livreurs).
- `POST /admin/orders/{id}/cancel` (dispatch, administrateurs) : annulation avant
  l'enlèvement, raison obligatoire, tracée et envoyée à l'expéditeur. La réattribution
  passe par `GET /admin/orders/{id}/candidates` et `POST /admin/orders/{id}/assign`.

## Cycle de vie d'une commande à sa création

- Paiement en espèces ou par le destinataire, sans créneau : la commande passe aussitôt en `SEARCHING_RIDER`.
- Prépaiement Mobile Money ou portefeuille : elle reste en `CREATED` jusqu'au paiement (phase 3).
- Créneau programmé : elle reste en `CREATED` et part en recherche de livreur 20 minutes avant le créneau.

Le code d'enlèvement (4 chiffres) n'est renvoyé qu'une fois, à la création ; s'il est perdu, `POST /orders/{id}/pickup-code` en génère un nouveau. Le code de livraison est créé à l'enlèvement et envoyé au destinataire (WhatsApp, ou SMS en repli). Après 5 codes faux saisis par le livreur, le code est bloqué : nouveau code d'enlèvement par l'expéditeur, validation de la livraison par le support.

## Photo du colis analysée

1. L'app envoie la photo : `POST /v1/media` avec `kind=PARCEL_PHOTO` (image, 1 Mo au plus).
2. `POST /v1/orders/parcel-analysis` `{ photoKey }` renvoie une proposition à faire confirmer : `suggestion` (taille `S`…`XL` ou `BULKY`, nature, précision en quelques mots, fragile), `prohibited` (objets interdits que la photo semble montrer, avec leur libellé), `isParcel` (faux : photo à reprendre) et `confidence`. Une photo n'est analysée qu'une fois (la même réponse ensuite). `503 PARCEL_ANALYSIS_UNAVAILABLE` ou `429 PARCEL_ANALYSIS_LIMIT` (`PARCEL_ANALYSIS_PER_HOUR` par compte) : l'expéditeur choisit lui-même.
3. La commande porte `parcelPhotoKey`. Si l'analyse a signalé un objet interdit, l'avertissement suit la commande : `parcelWarning` pour le livreur (avec `hasParcelPhoto` et `GET /v1/rider/orders/{id}/parcel-photo` tant que la course est en cours) et `parcel.aiWarning` au back-office.

Moteur : `PARCEL_VISION_PROVIDER=claude` (vision de Claude, `ANTHROPIC_API_KEY`, modèle `PARCEL_VISION_MODEL`, `claude-opus-5-5` par défaut, effort bas, sortie structurée), `fake` en développement, `none` pour couper l'analyse. Seule la photo est envoyée, jamais le nom ni le numéro.

## Modèle de prix : tarif pro et primes des livreurs (H4)

Tout se règle au back-office, sans nouvelle version des apps : le devis est toujours calculé par le serveur et affiché avant la commande.

- **Grille de lancement de Douala** (moto) : 1 000 F jusqu'à 5 km, +100 F par km commencé jusqu'à 10 km (paliers d'un km), puis +50 F par km (`perKmBeyondLastTier`). Part du livreur : 70 % (`riderShareBps: 7000`, valeur par défaut d'une grille).
- **Tarif pro** : une boutique (mode marchand) a une remise selon ses livraisons réussies du mois en cours, heure du Cameroun (par défaut −10 % dès 100, −15 % dès 300). Arrondie à 50 F, prise sur la part de Tara (la part du livreur ne change pas). Jamais cumulée avec un code promo : le plus avantageux est retenu, et un code moins avantageux n'est pas consommé. Le devis renvoie `discountSource` (`PROMO`, `VOLUME` ou `null`) et `proDiscountBps` ; la commande garde `proDiscountBps`.
- **Prime d'approche** : quand le vendeur est au-delà d'une distance (3 km par défaut) du livreur au moment de la proposition, Tara ajoute un montant (200 F par défaut).
- **Prime de renfort** : montant ajouté à chaque course proposée pendant une période (pluie, heures de pointe), au lieu d'augmenter le prix du client. Plusieurs primes qui se chevauchent ne se cumulent pas : la plus forte s'applique.
- Les primes sont annoncées dans la proposition (`approachBonus`, `boostBonus` ; `riderEarning` est le gain total), figées sur la commande quand le livreur accepte (ou quand le dispatch l'attribue, depuis sa dernière position), remises à zéro s'il rend la course, et payées à la livraison sur le compte `platform:expense:rider_bonuses`.

Routes (`ADMIN`, double authentification) : `GET` et `PUT /admin/pricing-settings/{ville}` (paliers du tarif pro, montant et seuil de la prime d'approche ; `updatedAt: null` tant que les valeurs validées s'appliquent), `POST /admin/pricing-grids/simulate` (prix, part du livreur et part de Tara d'une grille en projet pour quelques distances). Primes de renfort (`ADMIN` ou `DISPATCHER`) : `GET` et `POST /admin/rider-boosts`, `POST /admin/rider-boosts/{id}/cancel` (les courses déjà acceptées gardent leur prime). Une prime créée par un répartiteur est signalée par SMS aux administrateurs.

Boutiques (`ADMIN`, `FINANCE`) : `GET /admin/merchants?q&page` (les plus actives du mois d'abord : livraisons réussies du mois, tarif pro atteint, solde, dernière commande ; `onProRate` compte les boutiques au tarif pro), `GET /admin/merchants/{id}` (30 derniers jours, prochain palier du tarif pro, dernières commandes et reversements). Zones : `GET /admin/zones` liste aussi les zones coupées ; `GET /admin/zones/map` donne les contours de toutes les zones (quartiers et zones coupées compris) pour la carte où l'équipe dessine une nouvelle zone (`POST /admin/zones`, contour vérifié : `422 ZONE_GEOMETRY_INVALID` s'il se croise).

## Indicateurs (H7)

`GET /admin/metrics?days=7|30|90` (toute l'équipe ; 30 par défaut), heure du Cameroun, comparés à la période précédente de même durée : livraisons réussies par jour (avec échecs, retours, annulations), taux de réussite (livrées / livrées + retournées) et réussite au premier passage, délais médians et « 9 sur 10 » (trouver un livreur, trajet, total ; hors courses programmées, horodatages incohérents écartés), reversements aux boutiques faits le jour même, livreurs actifs et courses par livreur et par jour, cinq livreurs les plus actifs, fidélité des boutiques (actives la période d'avant et encore actives), journées du contrôle des comptes avec écarts, note moyenne reçue par les livreurs et livreurs sous 4/5.

## Équipe et audit (H8)

Routes `ADMIN` (double authentification) :

- `GET /admin/team` : membres de l'équipe, rôles, double authentification configurée ou non, dernière connexion.
- `POST /admin/team` `{ phone, fullName, roles }` : donne l'accès à un numéro (compte créé s'il n'existe pas, sinon rôles ajoutés). La personne se connecte ensuite au back-office avec son numéro et configure sa double authentification.
- `PUT /admin/team/{userId}/roles` : remplace les rôles d'équipe ; les sessions du membre sont fermées pour que les nouveaux droits s'appliquent tout de suite.
- `DELETE /admin/team/{userId}` : retire l'accès (rôles d'équipe, sessions, double authentification). Il reste toujours un administrateur (`422 TEAM_LAST_ADMIN`) et personne ne retire ses propres droits d'administrateur (`422 TEAM_SELF_DEMOTION`).
- `GET /admin/audit-log?entityType&entityId&actorId&cursor&limit` : journal des actions sensibles, les plus récentes d'abord, avec l'auteur, l'avant et l'après ; `entityTypes` liste les types d'objets présents pour le filtre. Le journal ne peut être ni modifié ni effacé (règle de la base de données).

## Gros objets (frigo, cuisinière, matelas…)

- Taille `BULKY` (« Gros objet ») : la course se fait en tricycle ou en voiture, jamais à moto. Le prix vient de la grille **tricycle** de la ville (`vehicleType: TRICYCLE` dans `POST /admin/pricing-grids`), distincte de la grille moto ; le devis renvoie `vehicleType`.
- `loadingHelp: true` (devis et commande) : l'expéditeur demande deux personnes pour charger ; le supplément `HANDLING` de la grille s'ajoute. Sans effet sur un colis ordinaire.
- Pas de grille tricycle active dans la ville : devis et commande refusés (`422 BULKY_UNAVAILABLE`).
- Attribution : un livreur à moto est écarté (`VEHICLE` dans `GET /admin/orders/{id}/candidates`), y compris à la main (`422 VEHICLE_NOT_SUITABLE`).
- Colis non conforme à l'enlèvement (trop grand, trop lourd, pas ce qui a été déclaré, objet interdit) : le livreur le refuse par `POST /v1/rider/orders/{id}/refuse-parcel` (motif, photo obligatoire, note facultative), pour tout colis et pas seulement les gros objets. La commande est annulée, la photo gardée comme preuve (`PICKUP_REFUSED`), et l'expéditeur paie le déplacement : le montant des frais de nouvelle tentative figés à la commande (`retryFee`), partagé comme une course entre le livreur et Tara. Après l'enlèvement : `409 PARCEL_REFUSAL_NOT_ALLOWED`.

## Attribution des courses (D1 à D4)

1. Dès qu'une commande passe en `SEARCHING_RIDER`, elle est proposée au livreur en ligne le mieux placé : distance d'approche, courses en cours, espèces détenues et note.
2. Il a 30 secondes pour répondre. Refus ou silence : la course part au suivant. Après 3 tours sans preneur, elle est diffusée à 5 livreurs à la fois ; le premier qui accepte l'emporte.
3. Le rayon de recherche s'élargit (3, 5, 8 puis 12 km). Sans livreur, nouvelle tentative toutes les 20 secondes ; après 5 minutes, le dispatch est alerté (temps réel et SMS d'astreinte), une seule fois.
4. Sont exclus : pièces manquantes ou expirées, plafond d'espèces atteint (en comptant les espèces de la course), 2 courses déjà en cours, une autre proposition en attente, véhicule trop petit pour un gros objet, alerte SOS encore ouverte (le livreur redevient disponible quand l'équipe clôt l'alerte). Un livreur qui a refusé ou rendu la course ne la revoit pas.

Le dispatcheur voit les livreurs proches et la raison de chaque exclusion (`GET /admin/orders/{id}/candidates`), l'historique des propositions (`GET /admin/orders/{id}/dispatch`), et peut attribuer ou réattribuer à la main (`POST /admin/orders/{id}/assign`) ; le livreur retiré est prévenu.

Tous les délais sont réglables par variables d'environnement (`DISPATCH_*`, voir `.env.example`).

## Notifications (F3)

- **Push** (Firebase Cloud Messaging) : l'app envoie son jeton après la connexion et à chaque renouvellement, `PUT /v1/me/devices/{installationId}/push-token` (`null` pour arrêter). Les propositions de course sont en priorité haute sur le canal Android `offers` (son et réveil écran verrouillé) ; les autres sur le canal `orders`. `data.type` indique l'écran à ouvrir.
- **Destinataire** (sans compte) : WhatsApp d'abord, avec des modèles approuvés par Meta nommés `tara_<modèle>` ; SMS si WhatsApp refuse le message ou signale plus tard un échec (webhook `POST /v1/webhooks/whatsapp`, signé).
- Messages par statut : confirmation au destinataire à la création ; push à l'expéditeur à l'attribution, à l'enlèvement, au départ, à la livraison, à l'échec, au retour et à l'annulation ; code de livraison puis reçu au destinataire ; au livreur, annulation ou retrait de sa course.

## Argent (G1 à G8, E5)

Montants en FCFA entiers. Chaque mouvement est une écriture du grand livre ; les soldes affichés en sont tirés.

**Frais Mobile Money.** Un client qui paie par Mobile Money (course, recharge, encaissement à la porte, frais de retour) paie en plus `mobileMoneyFee` = arrondi supérieur de montant × taux / (10 000 − taux), taux `MOBILE_MONEY_FEE_BPS` (600 pour un compte Sebpay particulier), donné aux apps par `mobileMoneyFeeBps` de `GET /v1/public/config` ; un paiement renvoie `amount` (dû à Tara), `mobileMoneyFee` et `total` (demandé sur le téléphone), l'encaissement à la porte donne `mobileMoneyFee`. Les recharges et dépôts des livreurs restent sans frais. Un reversement (boutique, livreur) est gratuit à partir du seuil du bénéficiaire (`FREE_PAYOUT_FROM`, ou celui fixé par la finance : `GET/PUT /v1/admin/finance/{merchants|riders}/{id}/free-payout`, avec la moyenne mensuelle des retraits pour repère, action tracée) ; en dessous, les frais Mobile Money (taux `PAYOUT_FEE_BPS`) sont partagés : le bénéficiaire en paie `PAYOUT_FEE_SHARE_PERCENT` % (50 par défaut, arrondi en sa faveur), retenus comme `withdrawalFee`, Tara le reste ; il reçoit `received` (`withdrawal.feeSharePercent` dans les portefeuilles). Tout le disponible peut toujours être retiré, même sous le minimum de 500 F ; une boutique à l'offre gratuite peut se faire reverser ainsi un petit solde. La suppression d'un compte est refusée tant qu'il reste un solde (`ACCOUNT_HAS_BALANCE`) ou un retrait en cours (`ACCOUNT_HAS_PAYOUT_IN_PROGRESS`) ; un livreur la demande au support, un administrateur la fait (`POST /v1/admin/riders/{id}/close-account`, mêmes garanties). Les remboursements des clients restent gratuits. Grand livre : frais facturés au compte `revenue:mobile_money_fees`, en face des frais du prestataire.

**Agrégateur Mobile Money.** `PAYMENT_PROVIDER=sebpay` (MTN Money et Orange Money au Cameroun, en XAF) avec `SEBPAY_PUBLIC_KEY`, `SEBPAY_SECRET_KEY` (clés `_test_` sur le bac à sable `SEBPAY_BASE_URL`, `_live_` sur `https://newapi.sebpay.bj/api/v1`) et `PUBLIC_API_URL` : Sebpay rappelle `POST {PUBLIC_API_URL}/v1/webhooks/payments/sebpay`, signé (`X-SebPay-Signature`, HMAC-SHA256 du corps brut avec la clé secrète), puis la transaction est relue par l'API avant d'être crue. L'opérateur suit le choix du payeur, sinon les premiers chiffres du numéro. Les frais d'encaissement sont lus au tarif du compte (`GET /c/calculate-fee`), ceux des reversements dans la réponse de Sebpay. L'adresse IP du serveur doit être déclarée dans le tableau de bord Sebpay (« Adresses IP autorisées », avec l'adresse du site) et validée par Sebpay : sinon `403 IP_NOT_ALLOWED`. Il faut donc un serveur à adresse sortante fixe.

**Paiement des frais d'une commande (G1).**

| `feePaymentMethod` (payé par l'expéditeur) | Ce qui se passe                                                                                                                                                                                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CASH`                                     | Payé au livreur à l'enlèvement ; la commande part tout de suite.                                                                                                                                                                                                                                             |
| `WALLET`                                   | Débité du solde Tara à la création (`INSUFFICIENT_BALANCE` sinon) ; pour un marchand, de son portefeuille.                                                                                                                                                                                                   |
| `MOMO_MTN`, `MOMO_ORANGE`                  | La commande reste `CREATED` ; `POST /orders/{id}/pay` envoie la demande au téléphone ; elle part à la confirmation. Lot (C4) : `POST /orders/batches/{id}/pay`, une seule demande pour toutes les commandes encore à payer, réparties à la confirmation (une commande annulée entre-temps revient au solde). |

Avec `feePayer: RECIPIENT`, le destinataire paie à la porte. Une commande annulée avant l'enlèvement rend ses frais au solde (avoir). Un retour que le destinataire devait payer est facturé à l'expéditeur. Un client dont le solde est négatif doit le régler avant de commander (`WALLET_IN_DEBT`) ; une boutique peut devoir jusqu'à 3 000 FCFA (`MERCHANT_DEBT_LIMIT`), au-delà ses nouvelles commandes attendent le règlement (`MERCHANT_DEBT_LIMIT`). Un compte endetté ne peut pas être supprimé (`ACCOUNT_HAS_DEBT`).

**Frais d'échec (E6).** Figés à la commande et annoncés au devis (`retryFee`, `returnFee` du devis et de `pricing`) : nouvelle tentative (supplément `FAILED_ATTEMPT` de la grille, 500 FCFA) et retour (supplément `RETURN`, la moitié du prix de base), à la charge de l'expéditeur et partagés comme la course (part du livreur de la grille). Une seule nouvelle tentative (`failure.retryAllowed`, sinon `RETRY_LIMIT_REACHED`). La tentative est prise sur le solde de l'expéditeur jusqu'à son plafond de dette (0 pour un particulier) ; au-delà, `RETRY_PAYMENT_REQUIRED` indique le montant à recharger (`POST /v1/me/wallet/topup`) avant de choisir. Retour : pas de paiement, pas de colis. Ce que le solde ne couvre pas (frais de retour, et la course si le destinataire devait la payer) est encaissé par le livreur à la remise (`GET /rider/orders/{id}/collection`, `reason: RETURN`, puis `POST /rider/orders/{id}/collect` en espèces ou par Mobile Money au téléphone de l'expéditeur) ; sinon `POST /rider/orders/{id}/return` répond `RETURN_COLLECTION_REQUIRED`. Le support peut clore un retour sans paiement (colis gardé au bureau).

**Encaissement à la porte (E5).** `GET /rider/orders/{id}/collection` donne ce qui reste dû (frais du destinataire et contre-remboursement). `POST /rider/orders/{id}/collect` avec `{ "method": "CASH" }` l'enregistre tout de suite (faisable hors connexion : `clientEventId`, `occurredAt`, position ; renvoyé, il est sans effet) ; avec `{ "method": "MOBILE_MONEY", "phone", "operator" }`, une demande part au téléphone du destinataire et la confirmation arrive par l'événement `payment.status` (ou `GET /payments/{id}`). La livraison est refusée (`COLLECTION_REQUIRED`) tant que tout n'est pas encaissé. Frais d'encaissement : 2 %, minimum 250 FCFA, déduits du montant reversé au marchand.

**Portefeuilles.**

| Qui      | Routes                                                                                                                                                                                                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client   | `GET /me/wallet` (boutique : encaissé aujourd'hui et livraisons du jour), `GET /me/wallet/transactions`, `POST /me/wallet/topup`, `POST /me/wallet/refund` (vers Mobile Money)                                                                                                                                                                      |
| Marchand | Idem avec `account=merchant` ; `POST /me/merchant/payouts` (à la demande, offres Pro et Business) ; `GET /me/payouts` ; `GET /me/merchant/statements/{AAAA-MM}` (PDF)                                                                                                                                                                               |
| Livreur  | `GET /rider/wallet` (solde prépayé `earnings`, mis de côté `reserved`, disponible ; espèces d'avant le solde prépayé : `cashHeld`, `cashDueBy`, `cashOverdue`), `POST /rider/topups` (recharge Mobile Money, frais payés par Tara), `GET /rider/wallet/transactions?account=earnings\|cash`, `POST /rider/withdrawals`, `POST /rider/cash-deposits` |

Le livreur garde sa part sur les espèces qu'il encaisse : son disponible au retrait vaut ses gains moins les espèces qu'il détient. Au-delà de son plafond d'espèces, il ne reçoit plus de courses tant qu'il n'a pas déposé.

**Reversements (G3).** Chaque jour à 18 h (heure du Cameroun), le portefeuille de chaque marchand en reversement quotidien part vers son numéro Mobile Money (500 FCFA minimum). Au-delà de 200 000 FCFA, un responsable financier valide d'abord. Un reversement échoué rend le montant au portefeuille.

**Solde prépayé du livreur (G5, décision 36).** Le solde (`earnings`) reçoit les gains et les recharges (`POST /rider/topups` par Mobile Money, crédité du montant entier : Tara paie les frais ; au bureau : `POST /admin/finance/riders/{riderId}/topups`). Une course avec encaissement (contre-remboursement, frais payés en espèces) n'est proposée qu'à un livreur dont le disponible la couvre (`BALANCE_TOO_LOW` sinon) ; à l'acceptation, le montant est mis de côté (`reserved`, `RIDER_BALANCE_TOO_LOW` si le solde a baissé entre-temps) ; à l'encaissement en espèces, il est pris sur le solde et le marchand est crédité aussitôt ; la réservation est libérée à la fin de la course ou si elle est retirée au livreur. Le solde ne devient jamais négatif. Disponible au retrait : solde − mis de côté.

**Espèces d'avant le solde prépayé.** Les espèces encore dues (`cashHeld`) se déposent sous 24 h (`CASH_DEPOSIT_DEADLINE_HOURS`), par Mobile Money (`POST /rider/cash-deposits`) ou au bureau ; rappel à 18 h ; en retard, plus de courses ni de passage en ligne (`CASH_OVERDUE`) ; 72 h de retard (`CASH_OVERDUE_SUSPEND_HOURS`) : compte suspendu, gains retenus sur la dette, SMS à l'équipe ; suspension levée par la finance.

**Back-office finance** (`ADMIN`, `FINANCE`, double authentification) : `GET /admin/finance/overview`, `GET /admin/finance/payouts?view=TO_APPROVE|IN_PROGRESS|FAILED|SENT|ALL` (bénéficiaire avec nom, téléphone et boutique, qui a validé et quand, nombre par vue dans `counts` ; `ALL` par défaut), `POST /admin/finance/payouts/{id}/approve` et `/reject`, `POST /admin/finance/riders/{riderId}/cash-deposits` (dépôt au bureau), `POST /admin/finance/users/{userId}/credits` (avoir), `POST /admin/finance/treasury-transfers`, `GET /admin/finance/reconciliations`, `POST /admin/finance/reconciliations/{jour}/run`, `GET /admin/finance/journal.csv?from&to` (export comptable, séparateur point-virgule), `GET /admin/finance/merchants/{merchantId}/statements/{AAAA-MM}`.

Notifications de l'agrégateur : `GET` ou `POST /v1/webhooks/payments/{prestataire}`, signées.
