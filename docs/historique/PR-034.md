# PR 34 · Temps réel : reconnexion après un jeton expiré pendant une coupure

Fusionnée le 2026-11-15 · branche `fix/temps-reel-reconnexion`

## Résumé

Constaté sur téléphone : après une perte de réseau, le bandeau « Hors connexion » de l'app livreur restait affiché pour de bon, alors que les pages se chargeaient normalement.

**Cause**

1. Le jeton d'accès (15 minutes) expire pendant la coupure.
2. Au retour du réseau, Socket.IO se reconnecte avec l'ancien jeton, et le middleware du serveur le refuse.
3. Après un `CONNECT_ERROR` envoyé par le serveur, `socket_io_client` détruit le socket (`active == false`) et n'essaie plus. Les requêtes REST, elles, renouvellent leur jeton : seule la connexion temps réel restait coupée.

**Correction**

- **`RealtimeClient`** (partagé par les deux apps) :
  - sur un refus du serveur, le jeton est renouvelé puis la connexion relancée, avec un délai croissant (2 s, 5 s, 15 s, 60 s) si le refus se répète ;
  - une erreur pendant le renouvellement n'empêche plus la reconnexion ;
  - rien n'est relancé après une déconnexion volontaire.
- **App expéditeur** : au retour de la connexion après une coupure, les livraisons en cours, l'historique et le portefeuille sont relus. Cela couvre les statuts manqués pendant la coupure et le message d'erreur resté affiché une fois les essais automatiques de Riverpod abandonnés.

## Vérifications

- Contre l'API locale, avec un jeton refusé au départ :
  - ancien code : toujours déconnecté après 20 s, aucun renouvellement ;
  - nouveau code : connecté en 2 s après un renouvellement.
- Nouveau test « au retour du réseau, la liste en erreur se recharge seule » : il échoue sans la correction et passe avec.
- `flutter test` : 322 tests pour l'app expéditeur et 445 pour l'app livreur ; `flutter analyze` et `dart format` OK.
