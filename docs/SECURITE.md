# Sécurité de Tara

Principes : défense en profondeur (chaque risque est couvert par au moins deux protections), moindre privilège, aucun secret dans le code, minimisation des données personnelles. Aucun système n'est inviolable : l'objectif est de rendre une attaque coûteuse, d'en limiter les dégâts et de la détecter vite.

## Menaces prioritaires et protections en place

| Menace                                       | Exemple                                                                    | Protections                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prise de compte client                       | Deviner un code SMS, voler un jeton                                        | Codes hachés, 5 essais par code, numéro bloqué 24 h après 10 échecs ; sessions de 15 min ; jeton de rafraîchissement à usage unique, toute réutilisation ferme toutes les sessions ; compte relu en base à chaque requête                                                                                                                                                                                                           |
| Prise de compte de l'équipe                  | Détournement de carte SIM (« SIM swap ») d'un administrateur               | Second facteur TOTP obligatoire ; sans vérification depuis moins de 12 h, les droits de l'équipe sont retirés sur toutes les routes ; anti-rejeu ; blocage après 5 échecs ; SMS d'alerte à l'activation et à la réinitialisation ; audit                                                                                                                                                                                            |
| Pompage de SMS                               | Faire envoyer des milliers de codes pour gonfler la facture                | Numéros camerounais uniquement ; plafonds par numéro, par adresse IP et global sur 24 h ; au plafond global, seuls les clients existants reçoivent un code ; alertes à 80 % et 100 %                                                                                                                                                                                                                                                |
| Téléphones de test                           | Lire les codes d'un numéro sans avoir le téléphone                         | Liste de 20 numéros au plus, choisie par root sur le serveur (`tara testeur`) ; messages gardés 24 h dans Redis, sur le réseau interne, lus par root seulement (`tara sms`) ; jamais un numéro de client réel, liste vidée avant l'ouverture au public                                                                                                                                                                              |
| Fuite de données personnelles                | Copie de la base, consultation abusive, journaux                           | Pièces d'identité chiffrées (AES-256-GCM, clé dérivée par usage) ; consultations auditées ; téléchargement en pièce jointe ; destinataires masqués après 30 jours ; journaux sans numéros ni jetons ; réponses non mises en cache                                                                                                                                                                                                   |
| Fraude financière                            | Payer moins, modifier une écriture, doubler un reversement                 | Prix recalculé par le serveur ; grand livre équilibré et en ajout seul, imposé par la base (trigger) ET par les droits ; idempotence ; verrouillage optimiste ; montant de chaque paiement contrôlé ; un seul reversement en cours par bénéficiaire ; validation par la finance au-delà d'un seuil ; rapprochement chaque nuit                                                                                                      |
| Faux paiements                               | Notification Mobile Money forgée ou rejouée                                | Signature du prestataire vérifiée en temps constant ; statut et montant relus auprès du prestataire quand la signature ne couvre pas le contenu ; chaque notification traitée une seule fois ; montant comparé à celui demandé                                                                                                                                                                                                      |
| Détournement d'espèces                       | Livreur qui garde l'argent encaissé                                        | Espèces détenues suivies dans le grand livre ; plafond par livreur, au-delà plus aucune course ; dépôt au bureau tracé et audité ; rapprochement des encaissements déclarés                                                                                                                                                                                                                                                         |
| Vol par compte détourné                      | Carte SIM détournée pour vider un portefeuille                             | Remboursements et retraits vers le seul numéro du compte ; numéro de reversement marchand modifié : reversements gelés 48 h et SMS à l'ancien numéro                                                                                                                                                                                                                                                                                |
| Fraude interne                               | Membre de l'équipe qui se crédite ou valide son propre reversement         | Avoirs, dépôts et validations interdits sur son propre compte ; double authentification ; journal d'audit de chaque opération                                                                                                                                                                                                                                                                                                       |
| Harcèlement par invites                      | Faire sonner le téléphone d'autrui avec des demandes de paiement           | Au-delà de 5 demandes sans réponse ou refusées en 10 minutes, le numéro n'est plus sollicité ; limitation par compte                                                                                                                                                                                                                                                                                                                |
| Compromission de l'API                       | Faille exploitée dans le code                                              | Compte de base restreint : pas de modification de structure, pas de désactivation des protections, pas d'accès à l'historique des migrations ; en-têtes de sécurité ; CORS fermé par défaut ; refus de démarrer avec une configuration dangereuse                                                                                                                                                                                   |
| Chaîne d'approvisionnement                   | Dépendance piégée ou vulnérable                                            | Versions verrouillées ; scripts d'installation des dépendances bloqués ; audit en CI ; Dependabot ; outils de CI épinglés et vérifiés par empreinte                                                                                                                                                                                                                                                                                 |
| Attaques web classiques                      | Injection SQL, fichier piégé, énumération                                  | Requêtes paramétrées ; validation de chaque entrée ; type réel des fichiers contrôlé ; jetons publics aléatoires de 128 bits ; « introuvable » pour les ressources d'autrui                                                                                                                                                                                                                                                         |
| Fraude à la livraison                        | Livreur qui devine un code, livraison déclarée sans remise                 | Codes à 4 chiffres hachés et bloqués après 5 erreurs (0,05 % de chances de deviner) ; photo et position GPS obligatoires ; livraison sans code validée par le support après appel, par un administrateur au-delà d'un montant ; trajet de chaque course enregistré (points non modifiables) avec alertes au support : action validée à plus de 200 m de l'adresse, long arrêt avec le colis, position simulée, trajet coupé ; audit |
| Faux échec de livraison                      | Livreur qui déclare « client absent » sans s'être présenté ni avoir appelé | Motif obligatoire, photo du lieu et position ; 2 appels au destinataire passés depuis l'app à 5 min d'écart (seuls comptent les appels de la tentative en cours, jamais dans le futur) ; échec déclaré à plus de 200 m de l'adresse signalé au support ; décision laissée à l'expéditeur ou au support (tracée)                                                                                                                     |
| Espèces non reversées                        | Livreur qui garde l'argent encaissé                                        | Solde prépayé (décision 36) : l'argent à encaisser est mis de côté sur le solde du livreur à l'acceptation et pris sur ce solde à l'encaissement, le marchand est crédité aussitôt ; le solde ne devient jamais négatif (comptes verrouillés à l'acceptation) ; espèces encore dues d'avant : dépôt sous 24 h, blocage, suspension ; audit                                                                                          |
| Abus du bouton SOS                           | Appuis répétés qui font envoyer des SMS en masse (coût, alertes ignorées)  | Maintien de 3 s ; 5 alertes par minute au plus ; une alerte déjà ouverte n'est pas doublée (l'équipe revoit la position, sans nouveaux SMS) ; renvoi au retour du réseau sans doublon (`clientEventId`)                                                                                                                                                                                                                             |
| Détournement du temps réel                   | Écouter la position d'un livreur, se faire passer pour lui                 | Connexion Socket.IO authentifiée par le même jeton que l'API, coupée à son expiration ; suivi d'une commande réservé à l'expéditeur, au livreur et à l'équipe ; débit limité par connexion                                                                                                                                                                                                                                          |
| Faux accusés de remise                       | Webhook WhatsApp forgé pour déclencher des SMS                             | Signature HMAC-SHA256 du corps brut vérifiée en temps constant ; un seul repli par message ; route désactivée sans configuration                                                                                                                                                                                                                                                                                                    |
| Téléphone du livreur perdu, volé ou espionné | Lire la session ou la file d'actions, intercepter le trafic                | Sauvegardes Android et transferts d'appareil désactivés ; HTTPS imposé (aussi sur Android 8 et 8.1) avec les seuls certificats du système ; code Dart obscurci dans les APK ; sessions dans le stockage chiffré du téléphone (étape 2)                                                                                                                                                                                              |

## Contrôles automatiques à chaque pull request

- Audit des dépendances de production : la CI échoue sur une vulnérabilité élevée ou critique.
- Recherche de secrets dans tout l'historique Git (gitleaks).
- Tests de sécurité (`apps/api/test/security.db-spec.ts`, `privacy.db-spec.ts`, `db-guards.db-spec.ts`), exécutés avec le compte restreint de la base.
- Garde de toutes les routes (`route-guards.db-spec.ts`) : chaque route `/admin` est réservée à des rôles de l'équipe, et seules les routes publiques revues une à une s'ouvrent sans connexion.
- Lint strict, typage, contrat OpenAPI à jour.

Dépendance de développement signalée et acceptée : `minimatch` (gravité modérée), utilisée seulement par l'outil de build NestJS, absente de l'API en production.

## Secrets et clés

Les secrets vivent sur le serveur, jamais dans le dépôt : tirés au hasard par `tara install` dans `/opt/tara/compose.env` (mots de passe internes) et `/opt/tara/api.env` (secrets de l'API et clés des prestataires saisies par `tara config`), lisibles par root seulement (voir [`DEPLOIEMENT.md`](DEPLOIEMENT.md)). Les valeurs de `apps/api/.env.example` sont factices.

La clé d'API Firebase de `apps/rider/lib/firebase_options.dart` n'est pas un secret : elle identifie le projet et figure dans tout APK publié. Avant le pilote : la restreindre à l'app `cm.tara.rider` et à son empreinte de signature dans la console Google Cloud, et vérifier que Firestore et Storage, inutilisés, ne sont pas ouverts.

| Secret                       | Rôle                                                                  | Rotation                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `JWT_SECRET`                 | Signature des jetons d'accès                                          | Mettre l'ancien dans `JWT_SECRET_PREVIOUS`, le nouveau dans `JWT_SECRET`, déployer, retirer l'ancien 15 minutes plus tard. Aucune déconnexion.                                                                                                                                                                                            |
| `CODE_HASH_SECRET`           | Hachage des codes SMS et des codes colis                              | Possible à tout moment : les codes en cours deviennent invalides (régénérer les codes d'enlèvement des commandes ouvertes).                                                                                                                                                                                                               |
| `STORAGE_ENCRYPTION_KEY`     | Chiffrement des pièces KYC et des secrets TOTP                        | Mettre l'ancienne dans `STORAGE_ENCRYPTION_KEY_PREVIOUS`, la nouvelle dans `STORAGE_ENCRYPTION_KEY`, déployer, lancer `pnpm --filter @tara/api storage:rotate-key` (rechiffre tout, peut être relancé), retirer l'ancienne une fois le script terminé sans élément illisible. Garder l'ancienne clé avec les sauvegardes qu'elle chiffre. |
| Clé d'envoi de l'app livreur | Signature des APK (`TARA_RIDER_KEYSTORE_*` dans les secrets du dépôt) | Google Play signe l'app avec sa propre clé ; la clé d'envoi perdue ou volée se remplace sur demande dans la Play Console.                                                                                                                                                                                                                 |
| Mots de passe PostgreSQL     | Comptes `tara_migrator` et `tara_app`                                 | Rejouer `infra/postgres/roles.sql` avec les nouveaux mots de passe, puis redéployer.                                                                                                                                                                                                                                                      |

## Base de données en production

1. Créer la base avec un compte administrateur, puis exécuter `infra/postgres/roles.sql` (commande en tête du fichier).
2. Lancer `pnpm db:deploy` avec `MIGRATION_DATABASE_URL` (compte `tara_migrator`).
3. Rejouer `infra/postgres/roles.sql` pour appliquer les droits aux nouvelles tables.
4. L'API utilise uniquement `DATABASE_URL` avec le compte `tara_app`, en connexion chiffrée (`sslmode=require`).
5. Sauvegardes chiffrées, restauration testée chaque trimestre.

## Procédures humaines

**Équipe Tara**

- La double authentification s'active le jour même de l'attribution d'un rôle d'équipe. Ne jamais partager un code ni le QR code d'enrôlement.
- Téléphone perdu ou volé : prévenir un administrateur, qui réinitialise le second facteur (toutes les sessions sont fermées).
- Départ d'un membre : retrait des rôles le jour même.

**Support client**

- Ne jamais demander à un client de lire un code reçu par SMS : un code ne se donne qu'à l'application.
- Ne jamais changer un numéro de téléphone ni un numéro de reversement sur simple appel : vérification d'identité écrite.
- La validation d'une livraison sans code (E4) exigera une double validation au-delà d'un montant à fixer (phase 4).

**Développeurs et prestataires**

- Accès au dépôt et à l'hébergement limités au strict nécessaire, retirés en fin de mission.
- Aucune donnée de production sur les postes de travail.
- Contrats avec clause de confidentialité et de cession des droits sur le code.

## Réponse à un incident

1. **Détecter** : alertes des journaux (numéro bloqué, plafond SMS, second facteur bloqué, erreurs 500 avec leur identifiant de requête).
2. **Contenir** : suspendre le compte concerné, révoquer les sessions, changer le secret exposé.
3. **Évaluer** : grâce au journal d'audit, établir les données et les personnes touchées.
4. **Notifier** : l'APDP et les personnes concernées selon la loi n° 2024/017 (délais et forme à faire préciser par le juriste).
5. **Corriger et documenter** : correctif, test qui reproduit le problème, retour d'expérience écrit.

## Revue de sécurité de la phase 7 (13 novembre 2026)

Périmètre : back-office (H1 à H8) et routes `/admin`, modèle de prix (tarif pro, primes), routes publiques, dépendances, chiffrement du stockage. **Aucun défaut critique ni majeur.**

- **Droits** : les 73 routes `/admin` (sur 176) exigent un rôle de l'équipe (et donc le second facteur) ; vérifié par un test sur toutes les routes. Un administrateur ne peut ni se retirer ses propres droits ni supprimer le dernier administrateur.
- **Routes sans connexion** : 15, revues une à une (santé, textes légaux, configuration publique, connexion par SMS, pages par jeton aléatoire, avis signés des prestataires). Liste figée dans le test.
- **Traçabilité** : chaque action du back-office qui modifie quelque chose (tarifs, promotions, primes, zones, commandes, équipe, finance, support, livreurs) est inscrite au journal d'audit.
- **Entrées** : formes des zones validées par PostGIS, export comptable protégé contre les formules de tableur, requêtes SQL paramétrées, aucun HTML injecté dans les pages.
- **Back-office** : session chiffrée dans un cookie `httpOnly`, `SameSite=Strict` ; politique de contenu stricte avec nonce, pas d'affichage dans un cadre.
- **Dépendances de production** : aucune vulnérabilité connue (`pnpm audit`).
- **Corrigé** : rotation de la clé de chiffrement du stockage (lecture avec l'ancienne clé pendant la transition, script de rechiffrement testé, écriture atomique des fichiers).
